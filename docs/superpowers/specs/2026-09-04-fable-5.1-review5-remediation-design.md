# FABLE 5.1 Review 5 Remediation Design

## Status
Approved for implementation on 2026-09-04.

## Goal
Close the residual findings from the fifth FABLE 5.1 review without reopening already-completed FABLE 5.1 work or weakening immutable release history.

## Scope

### E1 — Yandex Direct Reports hardening
`plugins/yandex-direct/scripts/yd_report.py` must be brought onto the same credential/error-handling generation as the hardened Direct API helper while preserving Reports-specific asynchronous polling semantics.

Required behavior:
- OAuth is accepted only from `YANDEX_DIRECT_TOKEN`; there is no `--token` CLI option.
- HTTP error bodies are read with a 4096-byte cap and decoded with UTF-8 replacement semantics.
- `URLError` becomes an operational failure rather than an uncaught traceback.
- The Reports polling contract remains intact: 200 returns TSV, 201/202 poll using `retryIn`, one retry of HTTP 500 remains allowed, other terminal statuses fail.
- Transport/opener and sleep behavior are injectable at the helper boundary for deterministic tests.
- Secrets must not be emitted in errors.
- This is a read/report helper; no preview-bound mutation contract is introduced.

### E2 — SEO semantic test repair
Repair the internal-linking tests that currently pass before reaching the behavior their names claim to exercise.

Required behavior:
- Unknown endpoint rejection is tested with otherwise-valid candidate metadata.
- `exact_match_required=True` rejection is tested with otherwise-valid candidate metadata.
- Each test asserts the intended semantic failure, not merely any `ValueError`.
- Brittle full-dict assertions are relaxed where the contract is semantic and additive diagnostics are allowed.
- Production SEO code changes only if the corrected RED test exposes a real production defect. If no production behavior changes, Yandex SEO remains version `1.1.2`.

### E3 — Direct contract/freshness traceability
Increase executable traceability for Direct behavior already implemented.

Required contracts:
- Reports async/polling semantics and Reports credential/error handling.
- KPI provenance sidecar semantics for Direct Reports.
- Creation is not activation: documentation/contract traceability must preserve the distinction without inventing generic activation enforcement where the API workflow does not support it.
- Direct volatile official API/source references used as normative platform facts must use parser-compatible `Verified: YYYY-MM-DD` markers and be included in repository freshness controls when appropriate.

This task must not rename immutable historical release tags or introduce a new shared root HTTP client.

### E4 — Repository/documentation cleanup
Bring repository documentation and validation into alignment with the already-published FABLE 2.0.0 generation.

Required behavior:
- RU/EN root documentation must state that Direct/Metrika/Webmaster `2.0.0` releases are already published and immutable.
- Verification examples use `python -m compileall -q scripts` rather than manually enumerated `py_compile` files.
- Secret scanning must cover credential-like literals in committed dotenv-style files (for example `.env`/`.env.*`) without treating `.env.example` placeholders as real secrets merely because of the filename.
- SKILL path/traceability conventions must remain consistent with the repository standard; add validation only where an actual drift can be expressed without constraining supported plugin structure unnecessarily.

## Explicitly deferred
The following FABLE review observations are valid design topics but are not part of this maintenance increment:
- automatic rollback snapshots/pre-read artifacts for generic Direct mutations;
- generic bulk `>20` entity-set enforcement across heterogeneous Direct services.

Until a separate safety design defines those semantics, documentation must not present them as helper-level executable guarantees when they are agent/operator policy only.

## Version and release policy
- `yandex-direct`: patch bump `2.0.0` → `2.0.1` because E1 changes executable helper behavior and credential surface.
- `yandex-seo`: remain `1.1.2` unless corrected tests expose and require a production behavior fix; if production behavior changes, bump to `1.1.3`.
- repository maintenance release: `1.0.3`.
- Other plugin versions remain unchanged.
- Existing immutable releases/tags must never be retargeted.

## Delivery model
One isolated branch and one pull request implement E1–E4. Each executable behavior change follows RED → observed expected failure → minimal GREEN → regression GREEN. Documentation/contract-only changes are validated by repository tests and explicit contract guards.

## Release gate
Release publication is permitted only after:
1. branch CI is green on the exact final head;
2. final exact-head Codex review has no unresolved findings;
3. PR is squash-merged using an expected-head guard;
4. post-merge `main` CI is green;
5. release manifests/tags are confirmed absent before creation and immutable after publication.
