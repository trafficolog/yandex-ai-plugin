# OPUS review contract hardening design

**Date:** 2026-09-02  
**Status:** approved in-chat design, pending written-spec review  
**Base:** `main` at `0d6db3044d29ef7ecf9b4f464dda209bcac88764`  
**Target branch:** `opus-1.1.0-contract-hardening`

## 1. Purpose

This change set addresses the still-open findings from the completed independent OPUS 5 review after the `1.0.1` remediation release.

The goal is not to add new Yandex products or broaden Phase 7. The goal is to harden the current seven-plugin marketplace so that:

1. externally imposed result limits are represented in machine-readable outputs;
2. client-side request validation matches verified API constraints;
3. asynchronous Webmaster PRO-export behavior has explicit lifecycle and quota semantics;
4. Yandex Marketing evidence has an executable source-role contract and no misleading dead taxonomy;
5. volatile external assumptions have a real freshness detector rather than pinned-date tests;
6. major promises in `SKILL.md` are traceable to an implementation helper and a regression test.

This is a contract-hardening release, not an Operations / AI / Mobile phase.

## 5. Wordstat association coverage

### 5.1 Problem

`GetTop` allows up to 2000 phrase results but Wordstat returns at most 20 associations. The current helper returns associations as a normal list without a machine-readable indication that this relation may be truncated.

This is analytically unsafe because downstream agents can confuse a capped related-query relation with complete semantic coverage.

### 5.2 Contract

Add:

```python
MAX_ASSOCIATIONS = 20
```

`normalize_top_response(...)` returns a `coverage` object:

```json
{
  "coverage": {
    "associations_cap": 20,
    "associations_count": 20,
    "associations_truncated": true
  }
}
```

Rules:

- `associations_truncated = true` when `len(associations) >= MAX_ASSOCIATIONS`;
- `false` when fewer are returned;
- this is conservative: exactly 20 means the cap was reached, therefore completeness cannot be asserted;
- `results` and `associations` remain separate relation types;
- no extrapolation from 20 associations to total semantic demand is allowed.

### 5.3 Documentation

`references/semantics.md`, current API/limits reference and relevant skills must state:

- associations are a capped relation;
- 20 returned associations are not proof of exhaustive semantic coverage;
- downstream SEO/Marketing use must preserve the coverage limitation.

### 5.4 Tests

Required RED→GREEN cases:

- response with 20 associations => `associations_truncated == true`;
- response with 5 => `false`;
- cap value is 20;
- relation labels remain unchanged;
- no helper sums association counts into market demand.

## 6. Wordstat Dynamics operator policy

### 6.1 Problem

The existing weekly/monthly rule is an approved conservative compatibility choice, but some references and skills incorrectly attribute it to Yandex Search API operator documentation, which describes a different operator language.

### 6.2 Decision

Do **not** broaden weekly/monthly runtime support in this release solely because a verified Yandex Wordstat source for those operator combinations is absent.

Keep the conservative runtime behavior:

- `PERIOD_DAILY` supports the documented Wordstat operator surface already allowed in `1.0.1`;
- weekly/monthly may reject non-`+` operator expressions under the repository's conservative compatibility rule.

But all documentation must describe this accurately as:

> repository-level conservative compatibility policy; not a documented Yandex API prohibition.

Remove the incorrect dependency on the web-search operator page as evidence for Wordstat behavior.

### 6.3 Output semantics

When a weekly/monthly expression is rejected, the error should say that the restriction is a plugin compatibility guard rather than claiming Yandex forbids the request.

### 6.4 Tests

- existing conservative reject behavior remains stable;
- error text does not claim an official Yandex restriction;
- `PERIOD_DAILY` remains allowed for non-`+` Wordstat operators.

## 7. Search result-depth contract

### 7.1 Problem

Current request validation accepts combinations such as 100 groups × 3 documents = 300 requested documents even though the documented result ceiling is 250.

The result window is also finite across pages, and the helper must not create a snapshot that implies visibility beyond the supported depth.

### 7.2 Constants

Add an explicit API-derived constant in the Search request layer:

```python
MAX_RESULTS = 250
```

### 7.3 Request validation

For each request:

```text
requested_per_page = groups_on_page * docs_in_group
window_start = page * requested_per_page
window_end = window_start + requested_per_page
```

Rules:

1. `requested_per_page > 250` => reject;
2. `window_start >= 250` => reject because the requested page is wholly outside the supported depth;
3. `window_end > 250` => allow only if the request can still return a partial final window, but mark the request/snapshot with an explicit depth limitation; if current API behavior cannot guarantee that safely, reject instead. Implementation tests must choose one behavior based on current verified docs and encode it explicitly.

The implementation plan must resolve rule 3 before production code is written; no silent truncation is acceptable.

### 7.4 Snapshot metadata

Structured SERP snapshots must preserve:

- `max_supported_results: 250`;
- requested page/group configuration;
- whether the configured window reaches the API ceiling;
- absolute rank from `1..250` only.

No result beyond rank 250 may be represented as observed.

### 7.5 Tests

- 100×3 rejected;
- first-page legal configurations accepted;
- page entirely beyond 250 rejected;
- boundary behavior around rank 250 explicit;
- competitor/ranking helpers cannot claim observations beyond the recorded depth.

## 8. Webmaster PRO export request correctness

### 8.1 `use_pro_tariff`

The request body uses the documented string representation:

```json
"use_pro_tariff": "true"
```

or:

```json
"use_pro_tariff": "false"
```

The public Python argument may remain boolean for caller ergonomics; serialization converts it to the API representation.

### 8.2 Path validation

Every `paths` item must:

- be a non-empty string;
- start with `/`;
- not be a full URL;
- preserve the exact path/query value after validation unless the API reference requires further normalization.

Invalid examples such as `https://example.com/blog` fail before network execution.

### 8.3 Tests

- `False` serializes to `"false"`;
- `True` serializes to `"true"`;
- `/blog` accepted;
- full URL rejected;
- path without leading slash rejected.

## 9. Webmaster PRO export lifecycle and quota semantics

### 9.1 Goal

Bring Webmaster asynchronous export handling to the same maturity level as Search deferred operations without inventing automatic polling or spend behavior.

### 9.2 Constants/reference metadata

Represent verified operational facts in one helper/reference layer:

- normal preparation guidance: about 20 minutes to 2 hours;
- long-tail preparation can take up to 24 hours;
- completed download URL lifetime: 24 hours;
- base request allowance: 100/day;
- PRO additional allowance: 500,000/month;
- base allowance is consumed first where current documentation states so.

These values are volatile and therefore must carry `verified_at` provenance in references and be covered by freshness checks.

### 9.3 Lifecycle helper

Add pure helper behavior comparable to Search retention state, for example:

```python
export_state(response, *, started_at=None, now=None)
```

Output should distinguish at minimum:

- `PENDING`;
- `READY`;
- `FAILED` when supported by response semantics;
- `DOWNLOAD_URL_MISSING` when status says success but URL is absent;
- `DOWNLOAD_EXPIRED_OR_UNKNOWN` when age exceeds known URL lifetime or timing context is insufficient.

No endless polling loop is added.

### 9.4 Polling guidance

Helpers may return recommended lifecycle metadata, but must not automatically poll based only on quotas.

No arbitrary exact polling interval is encoded as platform truth unless the official API specifies one.

### 9.5 Quota planner

Add deterministic quota metadata/planning only; do not implement autonomous execution.

Inputs can include known current base/PRO usage supplied by the caller. Output states whether the planned operation fits the supplied budget and what quota class is involved.

Missing usage data => `QUOTA_USAGE_UNKNOWN`, not assumed availability.

## 10. Marketing evidence roles

### 10.1 Problem

The approved Marketing design requires overlapping observations to be side by side with explicit source roles, but `add_evidence` currently validates only evidence kind/source/metric.

### 10.2 Roles

Canonical role vocabulary:

```text
canonical
reconciliation_only
enrichment
```

Human-readable specialized meaning can be preserved in an additional field if needed, but core code uses the small stable vocabulary above.

### 10.3 Role assignment

`canonical_metric(metric, records)` remains the source-of-truth selector.

For evidence where the metric has a known canonical source:

- canonical source record => `role: canonical`;
- overlapping noncanonical record of the same metric => `role: reconciliation_only`.

For non-overlapping contextual evidence such as SERP intent or Wordstat enrichment => `role: enrichment`.

`add_evidence` must either:

1. accept an explicit valid role, or
2. derive the role deterministically from metric/source using the canonical-source table.

Unknown ambiguous cases must not silently become canonical; use `enrichment` only when the evidence is genuinely contextual, otherwise reject or require explicit role.

### 10.4 Monetary evidence

For monetary metrics with a non-null numeric value (`cost`, `cpc`, `revenue`, and monetary derived observations where inserted as evidence):

- source is required;
- currency is required for cross-source comparison;
- VAT basis is required when it materially affects the metric;
- period must be preserved when supplied;
- date basis is preserved when supplied;
- missing required monetary context produces a validation error or an explicit noncomparable wrapper before reconciliation.

The implementation must not invent currency or VAT basis.

### 10.5 Reconciliation

`reconcile_metric` returns:

- all relevant records;
- canonical record;
- roles for each record;
- existing status (`ALIGNED`, `EXPLAINABLE_DIFFERENCE`, `REVIEW`, `INCOMPARABLE`).

No sum of canonical + reconciliation-only values is introduced.

## 11. Marketing finding taxonomy

### 11.1 Problem

The original approved design listed more finding classes than current deterministic helpers produce. `DEFAULT_GROUP_ORDER` and delegation currently make those dormant classes appear implemented.

### 11.2 Decision

Do **not** implement new analytical heuristics merely to make the taxonomy look complete.

Introduce explicit sets:

```python
IMPLEMENTED_FINDING_TYPES = {...}
DEFERRED_FINDING_TYPES = {...}
```

Only deterministic classes currently produced by tested helpers belong in `IMPLEMENTED_FINDING_TYPES`.

### 11.3 Prioritization

`DEFAULT_GROUP_ORDER` must contain only implemented classes.

If a finding type is not implemented but appears in externally supplied data:

- it sorts after known types;
- it is marked `UNKNOWN_OR_DEFERRED_TYPE` in priority metadata rather than receiving an implied approved semantic position.

### 11.4 Delegation

`delegate_action` may route only implemented finding types or explicitly approved externally-produced classes documented as such.

`NEW_CAMPAIGN_CANDIDATE` is removed unless it is added to the approved taxonomy in a future design.

No dead route remains simply because a name was once contemplated.

### 11.5 Documentation

The Marketing README/skills/reference taxonomy must clearly distinguish:

- implemented deterministic finding types;
- deferred future types;
- optional externally supplied context if any.

Deferred types are not advertised as current capabilities.

### 11.6 Tests

- every type in `DEFAULT_GROUP_ORDER` belongs to `IMPLEMENTED_FINDING_TYPES`;
- every delegated type is implemented/approved;
- deferred types never appear as locally-produced output in fixtures;
- `NEW_CAMPAIGN_CANDIDATE` has no live delegation route;
- implemented types remain stable against the actual `find_*` helpers.

## 12. API freshness control

### 12.1 Problem

Pinned strings such as `Verified: 2026-09-02` prove only that tests and docs agree. They do not detect an old assumption.

### 12.2 Verified marker

References that contain volatile API facts should expose a parseable marker in one of the supported forms:

```text
Verified: YYYY-MM-DD
verified YYYY-MM-DD
verified_at: YYYY-MM-DD
```

The validator owns the accepted syntax and tests it explicitly.

### 12.3 Freshness threshold

Default repository policy:

```text
MAX_REFERENCE_AGE_DAYS = 90
```

Rationale: API prices, quotas, models, retention windows, version paths and similar platform facts are sufficiently volatile to require a quarterly verification cadence, while a much shorter period would create excessive maintenance noise.

This is a repository maintenance policy, not a Yandex API rule.

### 12.4 Validator behavior

For references that declare a verification marker:

- parse the date;
- reject a future date;
- reject malformed dates;
- fail when age > 90 days;
- provide file path, verification date and age in the error.

The validator receives an injectable `today`/clock in unit tests so tests are deterministic.

### 12.5 Which files require markers

Not every prose file needs a date. Markers are required for references containing volatile external facts such as:

- API versions/endpoints when versioned;
- quota/price limits;
- result caps;
- attribution model lists/migration dates;
- asynchronous retention/lifetime limits;
- destructive-operation quotas.

Stable conceptual references may remain undated.

The contract matrix can identify which references are freshness-controlled.

### 12.6 CI

Repository validation runs on every PR and push as today; an expired freshness marker therefore makes the release gate fail until the fact is reverified and the marker updated.

No network access is performed by CI freshness validation. Human/model verification against official documentation is a release-maintenance activity, while CI checks recency and structure.

## 13. Executable contract matrix

### 13.1 Purpose

The independent review found that several promises in `SKILL.md` had no mechanical relationship to helpers/tests. The repository needs a traceability layer.

### 13.2 File

Add:

```text
docs/CONTRACT_MATRIX.json
```

A JSON source is preferred over Markdown as the authoritative machine-readable contract. A generated/readable Markdown view may be added later, but is not required for this release.

### 13.3 Schema

Version 1 shape:

```json
{
  "version": 1,
  "contracts": [
    {
      "id": "direct-write-preview",
      "plugin": "yandex-direct",
      "invariant": "Mutating Direct methods are preview-first unless explicitly executed.",
      "skills": ["plugins/yandex-direct/skills/yandex-direct-api/SKILL.md"],
      "helpers": ["plugins/yandex-direct/scripts/yd_api.py"],
      "tests": ["plugins/yandex-direct/tests/test_yd_api.py"],
      "references": ["plugins/yandex-direct/references/safety.md"],
      "freshness_controlled": false,
      "status": "implemented"
    }
  ]
}
```

Required fields:

- stable `id`;
- plugin;
- invariant description;
- at least one `skills` entry for skill-level promises, or an explicit reason when a contract is infrastructure-only;
- at least one helper/code path where applicable;
- at least one regression test;
- status from a small enum.

### 13.4 Status enum

```text
implemented
deferred
infrastructure
```

Rules:

- `implemented` requires skill/helper/test paths as applicable;
- `deferred` must not be advertised as a current capability;
- `infrastructure` is for validator/CI contracts without plugin helper semantics.

No free-form `partial` state is allowed because it would recreate ambiguous promises.

### 13.5 Initial coverage

The matrix must cover at minimum the highest-risk invariants already surfaced by OPUS:

- Direct preview-before-write;
- Metrika attribution omission/provenance;
- Webmaster feed batch body + destructive approval;
- Wordstat non-summing demand + association cap;
- Search top-depth + SERP presence not market share;
- SEO missing evidence / period / geography alignment;
- Marketing Direct-required routing;
- Marketing money-context compatibility;
- Marketing canonical/reconciliation roles;
- cross-service no-transport/no-credentials;
- eval expectation contract;
- API freshness policy.

The matrix is not required to list every helper function in 1.1.0. It is a traceability layer for declared behavioral invariants, with expansion expected in future maintenance releases.

### 13.6 Validator checks

The repository validator must verify:

- JSON schema shape;
- unique contract IDs;
- known plugin names;
- all referenced repository paths exist;
- every `implemented` plugin contract has test coverage path(s);
- every referenced `SKILL.md` path is valid;
- deferred contracts do not point to `DEFAULT_GROUP_ORDER`/available capability declarations where this can be checked deterministically;
- freshness-controlled references contain parseable verification markers.

The validator does **not** attempt semantic NLP comparison between prose and Python. It guarantees traceability and test linkage, not theorem proving.

## 18. Safety

This release adds no new live mutation ownership.

Existing invariant remains:

```text
read → analyze → preview → explicit approval → write → verify
```

Cross-service plugins remain transport-free and credential-free.

Marketing evidence-role changes are analytical only and must not create a path that executes delegated actions.

Webmaster PRO-export helpers may initialize a quota-consuming export only through the existing owning service write/preview contract; lifecycle helpers themselves are pure/read-oriented.

## 19. Definition of Done

The release is complete when all of the following are true:

### Wordstat

- association cap=20 is machine-readable;
- cap limitation is documented and tested;
- operator documentation no longer misattributes the conservative rule to Yandex Search operators.

### Search

- 250-result depth is enforced/represented in requests and snapshots;
- no structured observation claims rank beyond supported depth.

### Webmaster

- PRO body matches documented string/path contract;
- lifecycle and download-lifetime semantics are modeled;
- quota planning reports unknown usage honestly;
- no autonomous polling is introduced.

### Marketing

- overlapping evidence has explicit roles;
- canonical and reconciliation-only observations remain separate;
- taxonomy exposes only implemented current capabilities;
- dead delegation is removed;
- Marketing version is 1.1.0.

### Repository controls

- age-based freshness validation exists with deterministic tests;
- contract matrix exists and validator checks traceability;
- changed references carry current verification markers;
- root and plugin metadata reflect independent SemVer accurately;
- all nine CI jobs are green on the exact PR head;
- final PR has no unresolved review threads before merge.

## 20. Review mapping

This design intentionally responds to the final OPUS review conclusion that the strongest remaining risks were no skill/script correspondence mechanism and no freshness detector. It does so without pretending that a static matrix proves semantic equivalence: the matrix enforces explicit traceability, while regression tests remain the executable evidence.

The design also chooses not to manufacture missing Marketing findings solely for feature parity. A declared-but-deferred capability is safer and more honest than a new heuristic without an approved evidence rule.
