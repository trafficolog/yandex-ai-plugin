# OPUS review contract hardening design

**Date:** 2026-09-02  
**Status:** approved in-chat design, pending written-spec review  
**Base:** `main` at `0d6db3044d29ef7ecf9b4f464dda209bcac88764`  
**Target branch:** `opus-1.1.0-contract-hardening`

## 1. Purpose

This change set addresses the still-open findings from the completed independent OPUS 5 review after the `1.0.1` remediation release.

The goal is not to add new Yandex products or broaden Phase 7. The goal is to harden the current seven-plugin marketplace so that:

1. externally imposed result limits are represented in machine-readable outputs;
2. client-side validation matches verified API constraints;
3. Webmaster PRO export has explicit lifecycle and quota semantics;
4. Yandex Marketing has an executable evidence-role contract and an honest finding taxonomy;
5. volatile external assumptions have a real freshness detector;
6. major `SKILL.md` promises are traceable to helpers and regression tests.

This is a contract-hardening release, not an Operations / AI / Mobile phase.

## 5. Wordstat association coverage

### 5.1 Problem

`GetTop` can return many phrase results but the verified Yandex Cloud service limit caps associations at 20. Current normalized output does not say that the association relation can be truncated.

### 5.2 Contract

Add:

```python
MAX_ASSOCIATIONS = 20
```

`normalize_top_response(...)` returns:

```json
{
  "coverage": {
    "associations_cap": 20,
    "associations_count": 20,
    "associations_truncated": true
  }
}
```

Rules:

- `associations_truncated = true` when count is `>= 20`;
- fewer than 20 => `false`;
- exactly 20 is conservatively treated as cap-reached, not exhaustive;
- `results` and `associations` remain separate relation types;
- association counts are never summed into total market demand.

### 5.3 Downstream limitation

SEO/Marketing workflows that consume association evidence must be able to preserve a limitation equivalent to `WORDSTAT_ASSOCIATIONS_CAPPED` when the cap is reached. The service plugin owns the coverage fact; cross-service plugins only propagate it.

### 5.4 Documentation/tests

Update Wordstat semantics/API references and relevant skills. Tests must cover 20 => truncated, 5 => not truncated, cap=20, preserved relation labels, and no overlapping-frequency summation.

## 6. Wordstat Dynamics operator policy

### 6.1 Problem

The weekly/monthly compatibility restriction is an approved repository-level conservative choice, but some prose incorrectly presents it as a documented Yandex Search API operator restriction. The cited Search operator language is a different API surface.

### 6.2 Decision

Runtime behavior stays conservative:

- `PERIOD_DAILY` supports the Wordstat operator surface already allowed in `1.0.1`;
- weekly/monthly may reject non-`+` operator expressions under the plugin compatibility policy.

Documentation must call this a **repository compatibility guard, not a documented Yandex prohibition**.

Remove the web-search operator page as evidence for Wordstat behavior.

### 6.3 Error contract

Weekly/monthly rejection text must say that the plugin cannot guarantee compatibility for that expression/granularity and recommend a supported path. It must not claim Yandex forbids the request.

### 6.4 Tests

- current conservative rejection remains stable;
- error text does not attribute the rule to Yandex documentation;
- `PERIOD_DAILY` remains usable for non-`+` Wordstat operators.

## 7. Search result-depth contract

### 7.1 Verified external constraint

Yandex Cloud currently documents a maximum of **250 returned results** for Yandex Search API.

The existing helper can request more than that through grouping and can request pages whose configured result window crosses the maximum.

### 7.2 Constant

Add:

```python
MAX_RESULTS = 250
```

### 7.3 Window semantics

For request validation:

```text
requested_per_page = groups_on_page * docs_in_group
window_start = page * requested_per_page
window_end = window_start + requested_per_page
```

where `window_start` is zero-based and `window_end` is exclusive.

Rules are deliberately strict:

1. `requested_per_page > MAX_RESULTS` => reject;
2. `window_start >= MAX_RESULTS` => reject;
3. `window_end > MAX_RESULTS` => reject;
4. there is **no implicit partial-final-page behavior** because current verified documentation states the overall maximum but does not promise how an over-boundary grouped request is truncated;
5. callers that need the final supported slice must choose a configuration whose complete window ends at or before 250.

This means no helper depends on undocumented server leniency.

### 7.4 Snapshot metadata

Structured snapshots preserve:

- `max_supported_results: 250`;
- page/group configuration;
- `window_start` / `window_end`;
- `reaches_result_ceiling: true|false`;
- absolute observed rank only in `1..250`.

No ranking/competitor helper may present a position beyond 250 as observed evidence.

### 7.5 Tests

Required:

- 100 groups × 3 docs rejected;
- legal first-page configurations accepted;
- complete window ending exactly at 250 accepted;
- partial window crossing 250 rejected;
- page starting at/after 250 rejected;
- snapshot cannot contain an observed absolute rank >250.

## 8. Webmaster PRO export request correctness

### 8.1 Tariff serialization

The public Python argument may stay boolean, but API serialization is the documented string form:

```json
"use_pro_tariff": "true"
```

or:

```json
"use_pro_tariff": "false"
```

### 8.2 Path validation

Every `paths` entry must:

- be a non-empty string;
- start with `/`;
- not be a full URL;
- otherwise preserve the caller value unless current API docs require normalization.

A value such as `https://example.com/blog` fails before transport.

### 8.3 Tests

- booleans serialize to strings;
- `/blog` accepted;
- full URL rejected;
- missing leading `/` rejected.

## 9. Webmaster PRO export lifecycle and quota semantics

### 9.1 Verified response states

The verified status API uses the field:

```text
download_status
```

with documented states:

- `IN_PROGRESS`;
- `SUCCESS`;
- `FAILED`.

A `SUCCESS` response may contain `url`; the download URL is documented as available for 24 hours.

### 9.2 Verified operational limits

Current references must represent with verification provenance:

- normal preparation: about 20 minutes to 2 hours;
- exceptional preparation: up to 24 hours;
- completed URL lifetime: 24 hours;
- basic access: 100 request units/day;
- extended access: +500,000 request units/month;
- base access is consumed first;
- initialization response exposes quota-used/remaining fields and must be preferred over guessed usage when available.

These are volatile external facts and therefore freshness-controlled.

### 9.3 Lifecycle helper

Add pure deterministic interpretation, e.g.:

```python
export_state(response, *, completed_at=None, now=None)
```

Mapping:

- `IN_PROGRESS` => `PENDING`;
- `FAILED` => `FAILED`, preserving `error_code` / `error_message`;
- `SUCCESS` + HTTPS URL => `READY`;
- `SUCCESS` without URL => `DOWNLOAD_URL_MISSING`;
- if `completed_at` and `now` prove age >24h => `DOWNLOAD_EXPIRED`;
- if age cannot be established, do not call the URL expired: preserve `download_age: UNKNOWN`.

No undocumented task state names are introduced.

### 9.4 Polling behavior

No endless polling loop and no invented fixed interval. Helpers can state that the operation is asynchronous and expose observed status only.

### 9.5 Quota planning

Quota planning is deterministic and non-executing.

Inputs may be:

- requested dates/paths;
- initialization response quota fields when already available;
- caller-supplied known current quota state.

Outputs distinguish:

- `WITHIN_KNOWN_QUOTA`;
- `QUOTA_LIMIT_RISK`;
- `QUOTA_USAGE_UNKNOWN`.

Missing usage data is never treated as available quota.

## 10. Marketing evidence roles

### 10.1 Problem

The design requires overlapping metrics to carry source roles, but current evidence insertion does not enforce or derive them.

### 10.2 Stable role vocabulary

```text
canonical
reconciliation_only
enrichment
```

Specialized human-readable semantics may exist separately, but code uses these stable roles.

### 10.3 Canonical mapping

Existing canonical-source policy remains:

- Direct: paid impressions/clicks/cost/search-query context;
- Metrika: sessions/business outcomes/revenue/orders;
- Wordstat: demand;
- Search: optional SERP context.

For a metric with a known canonical source:

- canonical source => `role: canonical`;
- overlapping noncanonical source => `role: reconciliation_only`.

Contextual non-overlapping evidence => `role: enrichment`.

Unknown ambiguous evidence must not silently become canonical.

### 10.4 `add_evidence`

`add_evidence` must either accept a valid explicit role or deterministically derive one from metric/source.

Invalid roles fail validation.

Generic `metric: demand` remains forbidden.

### 10.5 Monetary context

For monetary observations used cross-source, preserve source, currency, VAT basis when material, period, date basis when known, and goal/attribution context when relevant.

No currency/VAT/date basis is invented. Missing material context leads to an explicit incomparable/limitation path rather than silent compatibility.

### 10.6 Reconciliation output

`reconcile_metric` returns:

- all relevant records with roles;
- selected canonical record;
- current reconciliation status (`ALIGNED`, `EXPLAINABLE_DIFFERENCE`, `REVIEW`, `INCOMPARABLE`);
- compatibility limitations.

Canonical and reconciliation-only values are never summed.

## 11. Marketing finding taxonomy

### 11.1 Problem

The approved design listed more finding classes than deterministic helpers currently produce. Old priority/delegation tables make dormant names look implemented.

### 11.2 Decision

Do not create new heuristics merely for taxonomy parity.

Add authoritative sets:

```python
IMPLEMENTED_FINDING_TYPES = {...}
DEFERRED_FINDING_TYPES = {...}
```

The implementation plan must derive the initial `IMPLEMENTED_FINDING_TYPES` from actual tested `find_*` outputs, not copy the old 18-name design list.

### 11.3 Priority order

`DEFAULT_GROUP_ORDER` contains only implemented local finding types.

Externally supplied unknown/deferred findings:

- sort after implemented classes;
- receive `UNKNOWN_OR_DEFERRED_TYPE` metadata;
- are not treated as approved local analytical output.

### 11.4 Delegation

`delegate_action` routes only implemented types or separately documented approved external classes.

`NEW_CAMPAIGN_CANDIDATE` is removed from delegation because it is neither in the approved taxonomy nor locally produced.

No dead route remains.

### 11.5 Documentation

Marketing README/skills/references distinguish:

- implemented deterministic classes;
- deferred future classes.

Deferred classes are not advertised as current capabilities.

### 11.6 Tests

- every default-priority type is implemented;
- every delegated type is implemented/explicitly approved;
- deferred types are absent from local produced fixtures;
- no `NEW_CAMPAIGN_CANDIDATE` route;
- actual `find_*` output set is covered by the declared implemented taxonomy.

## 12. API freshness control

### 12.1 Problem

A test that asserts the literal string `Verified: 2026-09-02` only proves that test and prose agree. It does not detect staleness.

### 12.2 Verification markers

The validator supports parseable markers such as:

```text
Verified: YYYY-MM-DD
verified YYYY-MM-DD
verified_at: YYYY-MM-DD
```

Accepted syntax is tested explicitly.

### 12.3 Repository policy

```text
MAX_REFERENCE_AGE_DAYS = 90
```

This is a repository maintenance policy, not a Yandex rule.

### 12.4 Validator semantics

For freshness-controlled references:

- parse date;
- malformed date => fail;
- future date => fail;
- age >90 days => fail with file/date/age;
- tests inject `today` so behavior is deterministic.

### 12.5 Which references are freshness-controlled

At minimum, references with volatile facts such as:

- API versions/endpoints;
- prices and quotas;
- result caps;
- attribution model lists/migration dates;
- asynchronous retention/download lifetime;
- write-operation quotas.

Stable conceptual prose need not carry a verification date.

### 12.6 CI behavior

CI performs no external web requests. Human/model release maintenance verifies facts against official sources; CI checks that declared verification is recent enough.

## 13. Executable contract matrix

### 13.1 Goal

Make high-risk `SKILL.md` promises mechanically traceable to implementation and regression tests.

### 13.2 Authoritative file

Add:

```text
docs/CONTRACT_MATRIX.json
```

JSON is authoritative. A human-readable generated view can be added later but is not required.

### 13.3 Version 1 schema

Example:

```json
{
  "version": 1,
  "contracts": [
    {
      "id": "direct-write-preview",
      "plugin": "yandex-direct",
      "invariant": "Mutating Direct methods are preview-first unless explicitly executed.",
      "skills": ["plugins/yandex-direct/skills/yandex-direct-api/SKILL.md"],
      "helpers": ["plugins/yandex-direct/scripts/yd_api.py"],
      "tests": ["plugins/yandex-direct/tests/test_yd_api.py"],
      "references": ["plugins/yandex-direct/references/safety.md"],
      "freshness_controlled": false,
      "status": "implemented"
    }
  ]
}
```

### 13.4 Status enum

```text
implemented
deferred
infrastructure
```

No ambiguous `partial` state.

Rules:

- `implemented`: real code path + regression test; skill path where the invariant is promised at skill level;
- `deferred`: not advertised as current capability;
- `infrastructure`: validator/CI contracts where a plugin helper is not applicable.

### 13.5 Initial required coverage

At minimum:

- Direct preview-before-write;
- Metrika attribution omission/provenance;
- Webmaster feed batch body/destructive safety;
- Webmaster PRO export contract;
- Wordstat no-sum demand invariant;
- Wordstat association cap;
- Search result depth;
- Search SERP presence != market share;
- SEO missing evidence/period/geo alignment;
- Marketing Direct-required routing;
- Marketing money compatibility;
- Marketing evidence roles;
- cross-service no transport/credentials;
- eval expectation contract;
- API freshness policy.

### 13.6 Validator checks

Validate:

- JSON shape/version;
- unique IDs;
- known plugin names;
- allowed statuses;
- referenced paths exist;
- `implemented` contracts have regression test paths;
- referenced `SKILL.md` files are real skill files;
- freshness-controlled references have valid markers;
- deferred Marketing classes are not simultaneously presented as implemented in machine-readable taxonomy.

The validator does not perform semantic NLP equivalence checking. The matrix guarantees traceability; regression tests are executable evidence.

## 20. Design rationale

The independent review's largest remaining systemic risks were not individual endpoint bugs but the absence of a freshness detector and the lack of a mechanical bridge between agent-facing promises and executable code/tests.

This design closes those structural gaps without claiming that a static matrix proves semantic equivalence. The matrix establishes traceability; regression tests remain the executable proof.

Likewise, Marketing does not manufacture missing finding classes to satisfy an old list. A clearly deferred capability is safer than a new heuristic with no approved evidence rule.
